# 이음이 — 어르신 디지털 안내 챗봇

로컬 RAG 파이프라인으로 만든 "어르신 디지털·스마트폰 이용 안내" 챗봇입니다.
메인퀘스트3(내 도메인에서 더 잘 대답해주는 RAG 챗봇 만들기) 과제로 만들었습니다.

## 주소가 둘입니다

같은 소스에서 두 벌을 만듭니다. 코드는 하나이고 빌드할 때 환경변수로 갈립니다.

| | 주소 | 답변을 만드는 곳 | 언제 되나 |
|---|---|---|---|
| **제출용** | https://nike1137-svg.github.io/Rag_guide_chatbot/ | 페이지를 연 **그 컴퓨터의 Ollama** | 항상 |
| **실사용판** | https://chat.dodami-ai.com | **운영자 노트북** | 그 노트북이 켜져 있는 동안만 |

**제출용**은 과제 요건대로 만든 것입니다. 브라우저가 보는 사람 컴퓨터의 Ollama를 직접 부르므로
채점자가 그대로 재현할 수 있고, 서버 상태와 무관하게 항상 동작합니다.
직접 질문하시려면 [사용 전 준비](#사용-전-준비)의 세 단계가 필요합니다.

**실사용판**은 어르신이 실제로 쓰시라고 따로 배포한 것입니다. 아무것도 설치하지 않고
주소만 열면 바로 질문할 수 있습니다. 다만 답변을 만드는 일은 운영자 노트북이 맡기 때문에,
**그 노트북이 꺼져 있거나 잠들어 있으면 답변을 드릴 수 없습니다.**
구조와 운영 방법은 [proxy/README.md](./proxy/README.md)에 적었습니다.

설치도 서버도 없이 결과만 보시려면, 두 주소 어느 쪽에서든 화면의
**"예시: 안내한 답변"** 버튼을 누르시면 실제로 실행해 기록한 결과를 볼 수 있습니다.

- 관련 문서: [PRD.md](./PRD.md) · [HANDOFF.md](./HANDOFF.md) · [proxy/README.md](./proxy/README.md)

## 서비스 소개

디지털배움터 이용 방법, 보이스피싱·스미싱 예방, 무인민원발급기·정부24 이용처럼
어르신이 자주 궁금해하는 질문에 공개 자료 15건에 근거해 답합니다.

자료에 없는 내용은 지어내지 않습니다. 근거가 약하면 조심스럽게 답하고, 범위 밖이면 거절합니다.

답변 아래에는 그 답을 만드는 데 쓴 자료가 칩으로 붙습니다. 칩에는 자료 번호(SD-004 같은),
어느 문서의 어느 대목인지, 어떻게 찾았는지(뜻이 비슷해서 / 낱말이 같아서), 얼마나 가까운지가 적혀 있습니다.
칩을 누르면 그 자료의 실제 문장이 그대로 나오고 원문 페이지로도 갈 수 있습니다.

## 실제 답변 예시

아래는 2026-08-30에 qwen3.5:2b으로 실제 실행해 기록한 결과입니다. 손으로 쓴 예시가 아닙니다.
배포 주소의 **예시: 안내한 답변** / **예시: 범위 밖 질문 거절** 버튼을 누르면 같은 내용을 화면에서 볼 수 있습니다.

잘 나온 답변만 고르지 않고 이 상태 그대로 기록했습니다.

## 사용 전 준비

이 앱은 정적 페이지입니다. 서버가 답변을 만들어 주지 않고, 페이지를 연 사람의 브라우저가
그 컴퓨터의 Ollama를 직접 호출합니다. 그래서 접속하는 쪽에 Ollama가 켜져 있어야 합니다.

### 1. 브라우저

Chrome이나 Edge를 쓰세요. Safari는 https 페이지에서 로컬 Ollama 호출을 막습니다.
Chrome이 "로컬 네트워크 접근"을 물으면 허용을 누릅니다.

### 2. Ollama 실행과 모델 준비

```
ollama serve
ollama pull qwen3.5:2b
ollama pull embeddinggemma
```

### 3. 배포 주소에서 열 때는 CORS 허용이 필요합니다

배포 주소에서 로컬 Ollama를 부르려면 Ollama 쪽에서 그 출처를 열어 줘야 합니다.
운영체제마다 한 번만 설정하고 Ollama를 재시작하면 됩니다.

macOS — 설정 후 메뉴 막대의 Ollama를 종료했다가 다시 실행합니다.
```
launchctl setenv OLLAMA_ORIGINS "https://*.github.io"
```

Windows — 설정 후 작업 표시줄에서 Ollama를 종료했다가 다시 실행합니다.
```
setx OLLAMA_ORIGINS "https://*.github.io"
```

Linux (systemd)
```
sudo systemctl set-environment OLLAMA_ORIGINS="https://*.github.io"
sudo systemctl restart ollama
```

서비스로 등록하지 않고 터미널에서 직접 `ollama serve`로 띄우셨다면 위 명령이 듣지 않습니다.
`ollama.service` 유닛이 없다는 오류가 나면 이 경우입니다. 그 프로세스를 끄고 환경변수를 붙여 다시 실행하세요.
```
pkill -f "ollama serve"
OLLAMA_ORIGINS="https://*.github.io" ollama serve
```

연결이 안 되면 화면에 "로컬 모델 미연결" 배너가 뜨고 위 명령이 그대로 나옵니다.
복사 버튼과 "다시 확인" 버튼도 함께 있습니다. 페이지가 고장 난 것인지 내 컴퓨터 설정 문제인지
사용자가 구분할 수 있어야 해서 넣었습니다.

## 화면에서 할 수 있는 것

- 연결 상태 칩과 미연결 배너 — Ollama 연결·모델 보유 여부를 표시하고, 실패하면 복구 명령과 재시도 버튼을 보여 줍니다
- 스트리밍 답변과 중지 — 토큰이 오는 대로 표시하고, 중지 버튼으로 생성을 끊을 수 있습니다
- 답변 안의 `[SD-000]` 인용 표시 — 지우지 않고 그대로 둡니다
- 출처 칩 — ID, 섹션, 검색 방법(의미 / 낱말 / 의미+낱말), 코사인 유사도를 함께 보여 줍니다
- 근거 원문 보기 — 칩을 누르면 그 자료의 실제 문장과 코사인·BM25 점수, 원문 링크가 나옵니다
- 약한 근거 경고 — 최고 유사도가 임계값 아래면 경고 배지가 붙고 말투가 조심스러워집니다
- 자동판정과 사람 피드백 — judge 6필드 결과와 좋아요/아쉬워요를 같은 화면에서 봅니다
- 접근성 — 큰 글씨, 고대비, 음성 입력, 답변 읽어주기
- 예시 미리보기 — Ollama가 없어도 실제로 실행해 기록한 답변 두 건(정상 안내 / 범위 밖 거절)을 그대로 볼 수 있습니다

이 중 근거 원문 보기, 검색 방법·점수 공개, 약한 근거 경고 배지, 모바일 반응형은
과제 기본 요구가 아니라 "조금 더 발전시키고 싶다면"에 제시된 항목을 구현한 것입니다.
답변이 그럴듯해 보이는 것과 실제로 근거가 있는 것은 다르기 때문에, 그 둘을 화면에서 갈라 보여 주려고 넣었습니다.

## 아키텍처

근거자료 15건(`senior-docs.source.json`)을 Ollama embeddinggemma로 미리 임베딩해
768차원 벡터스토어(`senior-docs.json`)로 만들어 둡니다. 질문이 들어오면 브라우저에서
코사인 + BM25 + RRF로 검색하고, 프롬프트를 조립해 로컬 qwen3.5:2b가 스트리밍으로 답합니다.
그 뒤에 LLM-as-a-Judge 자동판정과 사람 피드백이 붙습니다.

검색 계산은 브라우저에서, 질문 임베딩과 답변 생성은 로컬 Ollama에서 합니다.
배포는 GitHub Pages 정적 호스팅이라 서버 비용이 들지 않습니다.

검색은 임베딩 한 번 호출로 수십 ms 안에 끝나고 곧바로 답변 스트리밍이 이어집니다.
체감상 구분이 안 되기 때문에 '검색 중'과 '답변 생성 중'을 나누지 않고 하나의 진행 표시로 처리했습니다.

### 자료를 저장한 형식

공개 문서를 통째로 넣지 않고, 하나의 사실만 담은 단위로 잘라서 보관했습니다.
이 단위를 청크라고 부릅니다. 각 청크는 다섯 가지를 함께 들고 있습니다.

`id`(SD-001부터 연속 부여) · `text`(본문) · `url`(원문 주소) · `section`(원문 안에서 어느 대목인지) · `vector`(768차원 검색용 숫자)

본문만 남기고 출처를 버리면 답변이 어디서 왔는지 되짚을 수 없습니다. 그래서 URL과 섹션을 같이 저장했고,
화면의 출처 칩과 원문 보기가 이 값들을 그대로 씁니다. 현재 15건이고 가장 짧은 것이 121자, 평균 148자입니다.

## 근거 자료 (15건)

- 디지털배움터 소개·운영주체·교육대상·비용·장소·스마트폰/키오스크 교육·AI안전교육·방문교육·신청문의·부처문의처·수준별과정 (SD-001~SD-011)
- 보이스피싱 예방, 스미싱·문자사기 예방, 무인민원발급기 사용, 정부24 온라인 발급 (SD-012~SD-015)

## 임계값 설계

- `THRESHOLD = 0.33` — 최고 코사인 유사도가 이보다 낮으면 "근거가 약합니다" 경고를 붙이고 조심스럽게 답합니다
- `REFUSE = 0.30` — 이보다 낮으면 LLM을 아예 호출하지 않고 거절합니다
- `BM25_MIN = 6.0` — BM25 키워드 매칭이 이만큼 강하면 코사인이 낮아도 weak/refuse를 풀어 줍니다

임계값을 낮추는 대신 신호 자체를 하이브리드로 보강하는 쪽을 택했습니다.
BM25_MIN은 처음 2.0이었는데 실측 후 6.0으로 올렸습니다(아래 "BM25_MIN 취약점" 참고).

## 루브릭과 지금 값

고정 질문 30개(도메인내 20 / 애매 4 / 도메인밖 6)를 `eval.mjs`로 돌리고 judge 6필드로 채점합니다.

- 종합 점수 — 목표 80 이상, 지금 85.6
- 도메인내 20문항 — 목표 80 이상, 지금 88.8
- 애매 4문항 — 목표 70 이상, 지금 93.0
- 도메인밖 거절률 — 목표 100%, 지금 6/6
- 검색 정합(도메인내 오탐·도메인밖 누락) — 목표 0건, 지금 0건
- 출처 표시(cited) — 지금 0.63~0.70, 실행마다 흔들립니다

도메인밖 6문항은 전부 maxCos 0.17~0.26으로 LLM 호출 없이 거절됐고, judge도 6문항 모두 refusal로 봤습니다.

## 실험 기록

기본 과제는 파이프라인을 세우고 평가를 한 번 돌리는 데까지입니다.
그 위에 각 단계의 "더 깊이 갈 사람을 위한 길"로 제시된 항목들을 실제로 돌려 봤습니다.
아래 A/B 다섯 바퀴가 전부 거기서 나온 것입니다.

- 검색 단계 — top-k를 5·10·20으로 바꿔 상위 근거와 답변이 어떻게 달라지는지 기록, 약한 근거 임계값을 올려 보수성이 함께 움직이는지 관찰, RRF 융합을 조사해 도입
- 생성 단계 — 답변 모델을 더 큰 로컬 모델로 교체, 시스템 프롬프트 문구 A/B, temperature 변경에 따른 일관성 변화
- 판정 단계 — 같은 답변을 로컬 judge와 Gemini judge 양쪽에 보내 판정 비교

돌리지 못한 항목도 있습니다. WebGPU 실행 백엔드와 q4/q8 양자화 비교는 브라우저 WASM 임베딩을
포기하고 Ollama로 넘어오면서 해당이 없어졌고, judge 프롬프트 기준 문구 A/B와 쿼리 확장·리랭킹은
손대지 못했습니다.

실험은 "한 바퀴에 변수 하나" 규칙을 지켰습니다. 원본 스크립트는 그대로 두고 사본으로 실행한 뒤
산출물을 전부 커밋했습니다. 같은 30문항을 같은 순서로 다시 돌려야 행끼리 비교가 되기 때문입니다.

### A/B 실험 다섯 바퀴 (심화 과정)

| 실험 | 바꾼 값 | 30문항 평균 | 관찰 | 결정 |
|---|---|---|---|---|
| 임계값 | THRESHOLD 0.33 → 0.40 | 판정 변화 0건 | 최고 유사도가 0.33~0.40 구간에 걸린 문항이 없었음. 문항별 ±60 변동은 생성 비결정성 노이즈 | 0.33 유지 |
| top-k | K_VEC 5 / 10 / 20 | 75 / 80 / 83 | 5는 정답 출처가 누락돼 애매 문항이 54점까지 하락. 20은 개선 폭이 노이즈 수준 | 10 유지 |
| 프롬프트 문구 | 인용·한국어 규칙 강화 | 80 → 86 | 점수는 올랐으나 cited 지표가 0.70 → 0.63으로 하락. 과제 기준인 출처 표시와 상충 | 보류 |
| temperature | 기본 약 0.8 / 0.3 / 0.7 | 80 / 85 / 82 | 낮은 온도가 일관되게 유리. 0.3이 판정 변동 문항도 가장 적음(30개 중 8개) | 0.3 채택 |
| 모델 크기 | 답변 모델 0.8b / 2b / 4b | 60 / 85 / 측정 불가 | 0.8b는 cited 0.30, 애매 문항 39점. 4b는 GPU 없는 14GB 환경에서 gnome-shell·Xwayland 재시작(디스플레이 크래시) | 2b 유지 |

표에서 비교 기준으로 쓴 80점은 BM25_MIN을 6.0으로 올린 직후의 상태입니다.
**그 기준선 산출물은 남아 있지 않습니다.** temperature 0.3을 채택한 뒤 같은 파일(`eval-results.json`)에
재실행 결과를 덮어써서 지금은 85.6점짜리가 들어 있습니다. 실험군은 전부 별도 파일로 남겼는데
정작 대조군만 잃은 셈입니다. 지금 다시 돌려도 답변 생성에 비결정성이 있어 그때의 80점은 재현되지 않으므로,
숫자를 새로 채워 넣는 대신 못 남겼다는 사실을 적어 둡니다. 다음 실험부터는 기준선도 별도 파일로 남깁니다.

매 실험에서 바꾼 변수 외의 조건과 질문 순서는 고정했고, 채점하는 judge는 항상 temperature 0으로 두었습니다.
4b는 `ollama stop`으로 복구했습니다. 산출물은 `eval_ab_040.mjs`·`eval_topk05.mjs`·`eval_prompt.mjs`·`eval_temp03.mjs`·`eval_model08b.mjs`와
각각의 `eval-results-*.json`으로 남아 있습니다.

### 만들면서 발견해 고친 것들

**브라우저 WASM 임베딩 → Ollama 로컬 임베딩**
처음엔 transformers.js로 브라우저에서 직접 임베딩할 계획이었는데, 실습 환경 네트워크에서
CDN과 모델 호스트가 차단됐습니다. Ollama embeddinggemma로 바꿨고 "로컬에서 무료로"라는 취지는 그대로입니다.

**임베딩 접두어**
`title:`/`task:` 접두어를 붙이면 오히려 임베딩 분리도가 떨어지는 걸 확인했습니다(`compare_prefix.mjs`).
접두어 없이 원문 그대로 임베딩합니다.

**BM25 하이브리드와 RRF 융합 (심화 과정 — 검색 단계)**
"스미싱 문자 오면 어떻게 해요?"에서 코사인 유사도는 0.31로 낮은데 BM25는 2.10으로 강한 사례를 발견했습니다.
의미 검색이 놓치는 걸 낱말 검색이 잡은 경우입니다. 임계값을 내리는 대신 BM25_MIN 가드를 넣었습니다.
두 검색 순위를 합칠 때는 점수를 정규화해 더하는 대신 RRF(k=60)로 순위를 융합했습니다.
점수 크기가 검색마다 달라지는 BM25와 코사인을 같은 자리에 놓으려면 순위 기반이 안전하다고 봤습니다.

**한국어 전용 강제**
qwen3.5:2b가 한자·중국어를 섞어 답하길래 시스템 프롬프트에 "반드시 한국어로만"을 명시했습니다.

**judge 자기모순 관찰**
"교육비가 드나요?" 답변이 score 100인데 noHalluc은 false로 나왔습니다. 원본 자료와 대조해 보니
실제 환각이 아니었고, 언급된 내용이 SD-002에 그대로 있었습니다. 인용 표시 누락과
2B 모델의 필드 간 자기일관성 부족이 원인으로 보입니다.

**BM25_MIN 취약점 (2.0 → 6.0)**
평가 결과의 코사인 분포를 뜯어보니, 도메인 밖 질문인 "코스피 지수"와 "드라마 추천"이
코사인 0.19~0.22로 낮은데도 우연한 글자 겹침 때문에 BM25가 2.0을 넘어 거절을 빠져나가고 있었습니다.
직접 비교해 보니 진짜 매칭인 스미싱은 8.25, 우연 매칭인 코스피는 3.71, 드라마는 4.40이었습니다.
BM25_MIN을 6.0으로 올리고 30문항 재검증에서 도메인내 오탐 0, 도메인밖 누락 0을 확인했습니다.

**judge 이중화 (심화 과정 — 판정 단계)**
로컬 qwen3.5:2b와 Gemini 3.1 Flash-Lite(무료 티어)에 같은 30문항을 채점시켜 봤습니다.
평균은 로컬 86, Gemini 92로 6점 차이였습니다. 그런데 **문항별로 점수가 얼마나 벌어졌는지를 재보니
평균 15.6점**이었습니다. 평균끼리는 6점 차인데 개별 문항에서는 그보다 훨씬 크게 엇갈렸다는 뜻입니다.
점수차가 6점 이내인 문항은 절반뿐이었고, 판정 플래그 4종 일치율은 71%였습니다.
로컬 judge가 "조심스러운 표현"을 환각으로 과판정하는 편향도 함께 확인했습니다.

**평균만 보면 두 채점기가 비슷해 보이지만 문항 단위로는 전혀 그렇지 않습니다.**
점수 하나로 결론 내리면 안 된다는 근거가 여기서 나왔습니다.
로컬 judge를 유지합니다. 키는 커밋에 넣지 않고 스크립트가 `~/.config/gemini/api.key`에서 읽습니다.

## 실패 사례와 원인 단계

점수만 남기면 다음에 무엇을 고칠지 알 수 없어서, 어긋난 답변이 검색·생성·판정 중 어디에서 비롯됐는지 나눠 적었습니다.

| 사례 | 관찰된 값 | 원인 단계 |
|---|---|---|
| 도메인밖 2문항이 50점 ("손주 생일 선물", "고혈압에 좋은 음식") | refusal은 true인데 score 50 | 판정 — 정당한 거절인데 judge가 점수를 깎음. 거절 동작 자체는 6/6 정상 |
| noHalluc이 false인 문항 18건 | 대부분 score 80~100과 함께 나옴 | 판정 — 원문 대조 결과 실제 환각 아님. 2B judge의 편향 |
| "과학기술정보통신부에도 문의 가능?" 75점 | cited·noHalluc 모두 false | 생성 — 문장별 [ID] 누락. 내용은 SD-010 안에 있음 |
| cited false가 여럿 | 프롬프트 강화 실험에서도 개선 안 됨 | 생성 — 2B 모델이 모든 문장에 인용을 붙이지 못함 |
| 도메인밖이 BM25 우연 매칭으로 통과 (수정 전) | 코스피 3.71 / 드라마 4.40 | 검색 — BM25_MIN 2.0→6.0으로 해결 |

남은 실패는 대부분 판정 단계의 편향과 생성 단계의 인용 누락입니다. 검색 단계 실패는 BM25_MIN을 올리면서 없앴습니다.

## 알려진 한계

qwen3.5:2b는 2B 소형 모델이라 judge 6필드가 서로 어긋나는 경우가 있습니다. 답변 모델과 판정 모델이 같아서
독립 심사가 아니고, 교육용 거친 신호로 읽어야 합니다.

답변이 문장마다 [ID]를 완벽히 달지는 못합니다. 내용 자체는 근거자료 안에 있는 경우가 대부분입니다.
간헐적으로 중국어·한자가 섞이는 것도 남아 있습니다.

음성 입력은 완전한 로컬 처리가 아닙니다. Chrome의 Web Speech API는 음성을 Google 서버로 보내
인식하기 때문에 인터넷 연결이 필요하고 Firefox에서는 동작하지 않습니다.
답변 읽어주기는 브라우저 내장 기능이라 로컬에서 돌아갑니다.

검색·생성·판정은 전부 로컬 Ollama로 무료입니다. judge 이중화 실험의 Gemini만 외부 API를 썼고 무료 티어 안에서 돌렸습니다.

### 실사용판(chat.dodami-ai.com)에만 해당하는 제약

- **운영자 노트북이 켜져 있고 잠들지 않은 동안에만 동작합니다.** 꺼져 있으면 화면에
  "지금은 답변을 드릴 수 없습니다"가 뜹니다. 제출용과 예시 보기는 이와 무관하게 항상 동작합니다.
- 추론이 그 노트북 CPU(i5-10210U, GPU 가속 없음)를 씁니다. **첫 글자가 나오기까지 대략
  15~25초, 답변을 다 받기까지 1분 안팎**입니다. 여러 사람이 겹치면 순서대로 처리되어 더 걸립니다.
- 그래서 실사용판은 프롬프트에 넣는 근거를 3건으로 줄였습니다(제출용은 6건).
  검색 로직과 임계값은 양쪽이 같습니다.
- 자동판정(LLM-as-a-Judge) 버튼은 실사용판 화면에서 감춥니다. 채점 루브릭용 기능이라
  어르신께는 의미가 없습니다. 제출용에는 그대로 있습니다.

## 코드를 직접 실행해 보려면 (개발용)

배포 주소로 쓰는 데는 필요 없고, 저장소를 받아 코드를 고쳐 볼 때만 필요합니다.

```
cd app
npm install
npm run dev
```

http://localhost:5173/Rag_guide_chatbot/ 로 접속합니다. Node.js 18 이상이 필요합니다(내장 fetch 사용).

빌드는 두 가지입니다. 어느 쪽이든 `scripts/build.mjs`가 먼저 `VITE_*` 환경변수를 전부 지우고
필요한 값만 다시 넣습니다. PowerShell의 `$env:` 가 창에 남아 두 빌드가 섞이는 사고를 막기 위한 것입니다.

```
npm run build:submit   # 제출용. 환경변수 없이 빌드해 지금 게시된 것과 같은 동작이 나온다
npm run build:live     # 실사용판. app/.env.live 의 값을 읽는다 (커밋 대상 아님)
```

`app/.env.example`에 환경변수 여섯 개의 뜻과 기본값을 적어 두었습니다.
값을 하나도 주지 않으면 제출용 동작 그대로입니다.

## 평가 재현

```
node eval.mjs
```

같은 폴더에 `eval-results.json`으로 30문항 전체의 검색·답변·판정 결과가 저장됩니다.
현재 설정(THRESHOLD 0.33, BM25_MIN 6.0, temperature 0.3) 기준 평균 85.6점입니다.
답변 생성에 비결정성이 있어 실행마다 점수가 조금씩 달라집니다.
